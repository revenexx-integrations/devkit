# Documentation structure and content

How to write the *content* of a repo's TechDocs — the structure, the audience for each
page, and what belongs where. The goal is docs a new engineer or a consumer of the service
can actually use, not an autogenerated stub.

## Audience first

Every page is written for one primary reader. State it implicitly by what you include and
omit. The four readers that recur:

| Reader | Wants | Page |
| --- | --- | --- |
| **First-time visitor** | What is this, why does it exist, is it what I need | `index.md` |
| **New team member** | Get it running locally, make a change | `getting-started.md` |
| **Reviewer / adjacent team** | How it fits the system, dependencies, boundaries | `architecture.md` |
| **Consumer of the service** | How to call it, contracts, examples | `api.md` / usage section |
| **On-call / ops** | Diagnose and fix a live problem fast | `runbooks/*.md` |

Do not mix audiences on one page. Setup steps do not belong on the architecture page;
troubleshooting does not belong in getting-started.

## Page set by component type

Choose pages by what the repo is — do not force every page onto every repo.

- **service** (backend/API): `index`, `getting-started`, `architecture`, `api` (or usage),
  `runbooks/operations`.
- **website / frontend**: `index`, `getting-started`, `architecture`. Runbook only if it
  has its own operational concerns.
- **library / SDK**: `index`, `getting-started` (install + usage), and an API/usage
  reference. Usually no runbook.

Start with `index.md` + `getting-started.md` for every repo; add the rest as the repo
warrants. A short honest doc beats a long templated one full of `TODO`s.

## What each page contains

### index.md
- One paragraph: what it is, the problem it solves, who it is for.
- Where it sits in the platform (one line, link to `architecture.md`).
- Quick links: production URL, repo, related dashboards/tickets.
- Keep it short — it is a signpost, not a manual.

### getting-started.md
- Prerequisites (tools, access, env).
- Clone → install → configure → run, as copy-pasteable commands.
- How to verify it is working (a URL to open, a command whose output confirms success).
- How to run the tests. Target: a new engineer is running locally in under ~15 minutes.

### architecture.md
- A diagram (ASCII or an image in `docs/img/`) of the main pieces and data flow.
- Upstream/downstream dependencies and why.
- The System it belongs to and its siblings.
- Key decisions/trade-offs a reviewer needs to understand the shape of the code.

### api.md / usage
- For a service: endpoints or the OpenAPI reference, auth, a worked request/response example.
- For a library: public API surface, install snippet, a minimal usage example.
- Prefer one real example over exhaustive parameter tables.

### runbooks/*.md
- One file per operational concern or failure mode.
- Structure each failure as **Symptoms → Diagnose (numbered, with commands) → Fix**.
- Include where to look: log locations, dashboards, health endpoints.
- Written to be read at 3am under pressure — terse, imperative, no prose padding.

## Writing rules

- Imperative voice for instructions ("Run", "Set", "Open"), not "you should".
- Every command copy-pasteable; every referenced file/URL real.
- No placeholder pages in `nav` — an empty page is worse than a missing one.
- Keep language consistent within a repo (the revenexx default for code-facing docs is
  English; follow the repo's existing convention).
- Link across pages rather than repeating content.

## Reference examples in the backstage repo

The revenexx backstage repo's own `docs/` is a working model of this structure — read it
before writing new docs:

- `docs/index.md` — landing page done well (what/why + quick links).
- `docs/onboarding.md` — the canonical repo-onboarding steps.
- `docs/runbooks/mcp-server.md` — the Symptoms → Diagnose → Fix runbook pattern.
- `docs/api-guide.md` — the revenexx API-registration convention.
